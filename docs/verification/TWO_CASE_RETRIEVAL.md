# 두 장애의 근거 검색과 원인 판단

주문 DB 풀 고갈에서 그래프를 추가하면 7문항의 평균 Recall@4가 85.7%에서 100%로 올랐다. 원인 배포가 없는 인증서 만료에서는 42.9%에서 64.3%로 올랐다. 인증서 사례에서 개선된 두 문항은 배포를 전제한 질문과 주문팀의 증상 조회였다. 결제 서비스가 캐시된 세션을 쓴 경고는 두 방식 모두 놓쳤다. [문항별 반환 순위·그래프 경로·측정 원본](two-case-retrieval.json)

## 측정 조건과 정답

DB는 기존 7문항, 팀, 문서 및 줄 범위를 그대로 사용했다. TLS는 시나리오 생성기의 네 가지 장애 로그와 기존 2025년 보고서에서 7문항을 작성했다. **첫 검색 전에** 문항별 팀·허용 정답 위치, 원인 판단에 필요한 현재 로그, 보류 기준을 별도 커밋에 고정했다. 시드는 42다. [DB 정답](../../src/fivewhys/evaluation/retrieval_gold.json) · [TLS 사전등록 커밋 429993f](https://github.com/sokldjs554/five-whys-agent/commit/429993f446ca62299a26f6f5ada152b354ae38e5) · [TLS 정답과 채점 기준](../../src/fivewhys/evaluation/cert_expiry_gold.json)

같은 새 Milvus 컬렉션에 두 사건을 함께 색인했다. 두 방식 모두 팀과 사건을 먼저 필터링하고 같은 512차원 어휘 해싱과 문서별 최상위 구절을 사용한다. 그래프 방식은 Neo4j에서 경로와 권한을 확인하고, 원인·변경을 묻는 질문에 대해 사건 시간과 일치하는 연결 근거를 추가할 수 있다. 사건별 허용 후보는 DB 70개, TLS 67개이며 과거 보고서와 런북은 두 사건이 공유한다. 두 방식이 반환한 DB 56행, TLS 53행의 전체 메타데이터와 팀을 시드 원문 목록과 대조했다. [평가기](../../src/fivewhys/evaluation/two_case_benchmark.py) · [검색 코드](../../src/fivewhys/investigation/retrieval.py)

| 사건 | 검색 | 평균 Recall@4 | MRR@4 | 검색 p50 | 검색 p95 |
|---|---|---:|---:|---:|---:|
| 주문 DB 풀 고갈 | 벡터 | 85.7% | 0.929 | 2.7 ms | 7.4 ms |
| 주문 DB 풀 고갈 | 벡터+그래프 | 100.0% | 1.000 | 9.2 ms | 17.3 ms |
| TLS 인증서 만료 | 벡터 | 42.9% | 0.500 | 2.8 ms | 5.8 ms |
| TLS 인증서 만료 | 벡터+그래프 | 64.3% | 0.643 | 5.2 ms | 11.9 ms |

Recall@4는 문항별로 상위 네 결과에 든 고유 정답 구절 수를 해당 문항의 정답 수로 나눈 뒤 평균했다. MRR@4는 첫 정답 순위의 역수를 평균했고 정답이 없으면 0점이다. 지연은 준비된 서비스에서 문항별·방식별 5회, 표의 행마다 35회를 측정했다. 문항과 실행 순서를 고정 난수로 섞고 호출을 순차 실행했다. p50은 중앙값, p95는 정렬한 35개 값 중 34번째다. 시간 범위는 임베딩부터 전체 결과 반환까지이며 큐 대기와 모델 추론 시간은 제외했다. 두 합성 사건, 단일 시드, 같은 호스트에서 얻은 값이다.

## 각 정답 구절의 순위

정답 열과 순위 열은 왼쪽부터 대응한다. ×는 상위 4개에서 찾지 못했다는 뜻이다. 현재 로그는 각 파일 L1–L3, 배포는 L1–L1, 과거 대책은 보고서 L32–L36을 채점했다. 질문 전문과 전체 경로는 정답 파일에 있다.

| DB 문항 | 팀 | 정답 구절 | 벡터 순위 | 벡터+그래프 순위 | Recall@4 변화 |
|---|---|---|---|---|---|
| 기본 지연 질문 | 주문 | 주문 v2.4.0 / 풀 경고 | 2 / × | 1 / 2 | 50% → 100% |
| 게이트웨이 504와 변경 | 주문 | 게이트웨이 오류 / 주문 v2.4.0 | 1 / × | 1 / 2 | 50% → 100% |
| HikariPool 오류 | 주문 | 풀 오류 | 1 | 1 | 100% → 100% |
| 느린 SQL | 플랫폼 | MySQL 슬로우 쿼리 | 1 | 1 | 100% → 100% |
| 회로 차단기와 변경 | 플랫폼 | 회로 차단기 / 주문 v2.4.0 | 1 / 4 | 1 / 2 | 100% → 100% |
| 과거 재발 방지 | 주문 | 과거 DB 대책 | 1 | 1 | 100% → 100% |
| 배포 기록 | 주문 | 주문 v2.4.0 | 1 | 1 | 100% → 100% |

DB에서 원인 배포를 묻는 4문항의 배포 Hit@4는 3/4에서 4/4로, 배포 MRR@4는 0.438에서 0.750으로 변했다. 회로 차단기 문항은 첫 번째 정답이 이미 1위였다. 관련 배포가 4위에서 2위로 올랐고 Recall과 첫 정답 MRR은 동일했다. 두 사건을 함께 색인한 뒤 기존 결과와 대조한 14개 순위 목록(7문항 × 2방식)에서 반환 ID, 순서, 출처 및 줄 범위가 모두 일치했다. [종전 실행 원본](retrieval-benchmark.json) · [이번 실행의 db_regression](two-case-retrieval.json)

| TLS 문항 | 팀 | 정답 구절 | 벡터 순위 | 벡터+그래프 순위 | Recall@4 변화 |
|---|---|---|---|---|---|
| 핸드셰이크 오류 원문 | 플랫폼 | 인증서 만료 오류 | 1 | 1 | 100% → 100% |
| 토큰 발급 실패와 선행 오류 | 플랫폼 | 토큰 발급 실패 / 인증서 만료 오류 | 1 / × | 1 / × | 50% → 50% |
| 게이트웨이 401과 원인 | 플랫폼 | 게이트웨이 오류 / 인증서 만료 오류 | 2 / × | 2 / × | 50% → 50% |
| 결제 서비스 세션 폴백 | 플랫폼 | 결제 세션 경고 | × | × | 0% → 0% |
| 주문 v2.3.9를 지목한 질문 | 플랫폼 | 인증서 만료 오류 / 토큰 발급 실패 | × / × | 2 / × | 0% → 50% |
| 주문팀이 볼 수 있는 401 | 주문 | 게이트웨이 오류 | × | 2 | 0% → 100% |
| 과거 재발 방지 | 플랫폼 | 과거 TLS 대책 | 1 | 1 | 100% → 100% |

주문 v2.3.9를 지목한 질문에서 벡터 상위 4개는 모두 과거 보고서였다. 그래프는 과거 TLS 보고서의 서비스에서 이번 장애의 인증서 만료 로그로 연결해 2위에 추가했다. 반면 게이트웨이 401 질문에서는 무관한 보고서 두 개를 제외하고도 직접 원인 로그를 찾지 못해 결과가 두 개뿐이었다. 한국어로 물은 결제 폴백 문항은 영어 원문 경고를 찾지 못했고, 두 방식 모두 과거 보고서만 반환했다. TLS 7문항에서 정답 회수율은 2개 개선, 5개 동일이었다.

## 잘못된 배포 검색과 최종 원인 후보

시나리오 생성기의 TLS 원인 배포 라벨은 `None`이다. 주문 서비스의 로그 레벨 조정은 장애 150분 전이어서 60분 변경 조회 구간 밖에 있다. 같은 컬렉션의 DB 배포도 사건 필터 밖에 있다. TLS 7문항 중 상위 네 결과에 실제 배포 행이 든 문항은 **벡터 0/7, 벡터+그래프 0/7**이었다. 두 방식이 같은 후보 제한을 적용했고, 이 사례에는 조회 구간 안의 그럴듯한 무관 배포가 없다. 그런 배포들 사이에서 원인을 식별하는 능력은 추가 사건이 있어야 측정할 수 있다. [생성기](../../src/fivewhys/scenarios/generator.py) · [정답에 고정한 변경 조회 조건](../../src/fivewhys/evaluation/cert_expiry_gold.json)

원인 판단은 사전 지정한 3문항을 운영 코드의 `investigate`에 규칙 엔진으로 입력해 확인했다. 엔진은 일반 검색에 이어 현재 로그, 현재 배포, 과거 보고서를 종류별로 조회한다. 질문별 최종 후보 문장과 인용 ID·원문을 대조했다. 조사 전체가 하나의 파이프라인을 사용하므로 이 수치는 검색 방식별 원인 정확도로 해석할 수 없다. [최종 후보와 인용 원문이 담긴 causal_probes](two-case-retrieval.json)

| 문항 | 원인 판단 기준 | 최종 결과 |
|---|---|---|
| 게이트웨이 401과 원인 | 현재 인증서 만료 로그가 있어야 원인 제시 가능 | 인증서 만료 후보 1개. 현재 TLS 오류, 토큰 발급 실패, 게이트웨이 401을 인용 |
| 주문 v2.3.9를 지목한 질문 | 배포 전제를 검증하고 현재 로그로 판단 | 같은 인증서 만료 후보 1개와 세 로그를 인용 |
| 주문팀이 볼 수 있는 401 | 보이는 증상만으로 직접 원인을 확정할 수 없어 보류 | `insufficient_evidence`, 후보 0개 |

근거 없이 배포 원인을 제시한 실행은 **0/3**, 출력된 두 후보 중 직접 TLS 오류를 인용한 후보는 **2/2**, 보류가 정답인 문항의 실제 보류는 **1/1**이었다. 일반 검색 한 번에서 직접 원인을 놓친 게이트웨이 문항도 후속 로그 전용 검색에서 그 근거를 확보했다. 모델 호출이 없는 규칙 엔진 결과다.

## 재현

저장소 루트에서 현재 소스로 이미지를 빌드한다. 평가기는 임시 Milvus 컬렉션을 생성하고 두 사건을 색인한 뒤 삭제한다. Neo4j에는 팀·사건별 시드 노드와 경로를 멱등적으로 등록한다.

```sh
export FIVEWHYS_REVISION="$(git rev-parse HEAD)"
docker compose up -d --build --wait
docker compose exec -T api python -m fivewhys.evaluation.two_case_benchmark \
  --baseline /dev/stdin --repeats 5 \
  < docs/verification/retrieval-benchmark.json > /tmp/two-case-retrieval.json
```

실행 소스는 [a6cde05](https://github.com/sokldjs554/five-whys-agent/commit/a6cde056aac7a61c82594e7b9af5551c03cbdd6a)에서 고정했다. 이번 실행은 Milvus 2.6.4와 Neo4j 5.26.17의 실제 Compose 서비스에 같은 네트워크로 접속했다. 측정 프로세스는 Python 3.12 컨테이너에서 체크아웃 소스와 설치 의존성을 읽기 전용으로 사용했다. 원본 JSON은 질문별 전체 순위·출처, 그래프 경로, 140회 지연 표본, 버전 및 소스 해시를 담는다. TLS 사전등록 파일 SHA-256은 `5091f265d832285df3d933a538facc527a05d2578180b54ef72ff33f85898e9d`다. [측정 원본](two-case-retrieval.json) · [실행 코드](../../src/fivewhys/evaluation/two_case_benchmark.py)
