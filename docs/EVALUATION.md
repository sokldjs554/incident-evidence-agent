# 평가 방법론

## 문제의식

LLM 프로젝트에서 가장 흔히 빠지는 함정은 "출력이 그럴듯해 보인다"로 품질을
판단하는 것이다. RCA는 특히 위험하다 — 그럴듯하지만 틀린 근본 원인은 팀을
엉뚱한 방향으로 보내고, 존재하지 않는 로그를 인용하는 보고서는 신뢰를 무너뜨린다.

이 프로젝트는 평가를 시스템의 부속이 아니라 **설계의 출발점**으로 삼았다:
"정답을 아는 장애"를 만들 수 있어야 에이전트를 정량 평가할 수 있다.

## 합성 시나리오 설계

각 시나리오(`scenarios/generator.py`)는 다음을 함께 생성한다:

| 요소 | 내용 |
|---|---|
| 베이스라인 로그 | 정상 트래픽 60분 (서비스 7종, 평시 WARN 노이즈 포함) |
| 장애 로그 | 15분, 인과 순서가 있는 다단계 버스트 (원인 서비스 → 전파 → 게이트웨이) |
| 변경 이벤트 | 원인인 배포/설정 변경 + **무관한 노이즈 변경** (에이전트가 구분해야 함) |
| GroundTruth | 근본원인 서비스, 원인 서술 키워드, 원인 변경 식별자, 정답 인과 사슬 |

시나리오 5종: DB 커넥션 풀 고갈 / 메모리 누수 OOM / 디스크 고갈 /
TLS 인증서 만료(변경 무관 장애) / 캐시 스탬피드.

시드를 바꾸면 타임스탬프·파라미터가 달라지므로(구조는 유지) 같은 시나리오를
여러 번 평가해 흔들림을 볼 수 있다. 같은 시드는 항상 같은 데이터를 만든다(결정적).

## 채점 항목

| 항목 | 방식 | 잡아내는 실패 |
|---|---|---|
| root_service_correct | 정답 서비스와 정확 일치 | "에러가 가장 많은 서비스"를 원인으로 오인 (상관≠인과) |
| root_cause_keyword_hit | 원인 서술에 정답 키워드 포함 | 서비스는 맞췄지만 원인 설명이 엉뚱한 경우 |
| culprit_identified | 원인 변경 식별자 포함 여부 | 무관한 배포를 범인으로 지목 / 변경을 놓침 |
| evidence_precision | 인용 로그 id의 실존 + 장애 구간 포함 비율 | **환각 인용** (존재하지 않는 증거) |
| whys_depth | 왜? 체인 길이 (≥3 요구) | 표면 증상에서 멈춘 얕은 분석 |
| coherence (선택, LLM-judge) | 정답 인과 사슬과의 본질적 일치를 1~5점 | 논리 비약, 순서 뒤집힘 |

## 베이스라인의 역할

`ScriptedLLM`은 LLM 없이 같은 에이전트 루프를 도는 휴리스틱 엔진이다.
현재 시나리오 15회 실행(5종 × 시드 3개)에서 전 항목 만점을 받는다.

이것은 의도된 결과다:

1. **파이프라인 검증** — 채점이 만점을 낼 수 있다는 것은 저장소·도구·루프·채점의
   전 구간이 올바르게 맞물린다는 뜻이다 (평가 하니스 자체의 버그 검출).
2. **비용 0의 CI** — 에이전트 루프 회귀를 API 호출 없이 잡는다.
3. **정직한 기준선** — LLM 엔진이 베이스라인과 같은 점수라면 이 난이도에서는
   LLM이 불필요하다는 뜻이다.

## 실측: LLM 엔진 vs 베이스라인

`claude-opus-5`로 두 시나리오를 실행해 같은 하니스로 채점한 결과다.

| 지표 | scripted | Claude (db_pool_exhaustion) | Claude (cache_stampede) |
|---|---|---|---|
| 근본원인 서비스 | ✅ | ✅ order-service | ✅ redis-cache |
| 원인 변경 식별 | ✅ | ✅ v2.4.0 배포 | ✅ 노드 재시작 |
| 증거 정밀도 | 1.00 | 1.00 | 1.00 |
| 인용 로그 수 | 6 | 30 | 24 |
| 왜? 체인 깊이 | 3 | 5 | 6 |
| 분석 턴 수 | 5 | 6 | 4 |
| 자기 보고 신뢰도 | 60% | 93% | 93% |

**규칙 채점 항목은 동률이다.** 현재 시나리오 난이도에서 정확도는 변별력이 없다는
사실이 실측으로 확인됐다 — 위 3번 항목의 예측이 맞았다.

**판정은 재현되지만 경로는 매번 다르다.** `db_pool_exhaustion`을 두 번 실행한 결과:

| | 1회차 | 2회차 |
|---|---|---|
| 근본원인 / 원인 변경 | order-service · v2.4.0 | 동일 |
| 증거 정밀도 | 1.00 | 1.00 |
| 인용 로그 수 | 30 | 31 |
| 분석 턴 수 | 6 | 5 |

결론은 안정적이지만 도구 호출 횟수와 인용 집합은 실행마다 달라진다. 규칙 기반
채점이 필요한 이유가 여기 있다 — 출력이 매번 다르므로 "그럴듯해 보이는지"로는
회귀를 잡을 수 없고, 검증 가능한 항목(정답 서비스, 인용 id의 실존)만이
실행 간 비교 가능한 기준이 된다.

**차이는 채점표가 아직 재지 않는 곳에서 나타난다.** LLM 엔진은:

- 증거를 4~5배 더 인용하면서도 **환각 인용이 0건**이다 (정밀도 1.00 유지).
  인용량이 늘면 정밀도가 떨어지는 것이 일반적이므로, 이는 도구가 반환한
  실제 log id만 사용했다는 뜻이다.
- 인과 사슬을 **기술적 원인에서 멈추지 않고 조직적 원인까지** 내려간다
  (Why 5: "배포 전 EXPLAIN 검토 게이트가 CI에 없었다").
- **RAG로 찾은 과거 포스트모템과 현재 증거의 모순을 발견한다.**
  2025-11-14 문서에는 "[완료] customer_ref 인덱스 추가"로 적혀 있는데 같은 원인의
  장애가 재발했으므로, 스키마 드리프트 검사와 액션 아이템 이행 감사를 대책으로 제시했다.
  설계에 없던 추론이다.
- 대책이 시나리오 맥락에 붙어 있다 (커넥션 타임아웃 30s를 게이트웨이 10s보다
  짧게 조정, 주문 조회 경로 벌크헤드 분리 등). 베이스라인의 대책은 키워드 매칭
  템플릿이라 원리적으로 이런 제안을 할 수 없다.

### 이 결과가 남기는 과제

정확도로는 두 엔진을 구분할 수 없으므로, **채점표에 없는 차이를 채점 항목으로
끌어올리는 것**이 다음 작업이다:

1. 휴리스틱이 원리적으로 실패하는 시나리오 추가 (아래 로드맵) → 정확도 격차 생성
2. 대책 품질·인과 사슬 깊이를 LLM-judge 항목으로 상시 편입
3. 인용량 대비 정밀도를 함께 보는 지표 (많이 인용하면서 정확한 쪽을 보상)

## 로드맵: 휴리스틱을 무너뜨리는 시나리오

베이스라인 휴리스틱("가장 먼저 에러난 서비스 + 최근 변경 우선")이 구조적으로
실패하도록 설계할 다음 시나리오들:

- **오도하는 변경**: 장애 직전 무관한 배포가 에러 서비스에 존재 (변경≠원인)
- **다중 복합 원인**: 두 변경이 결합해야 장애가 되는 경우
- **로그에 없는 원인**: 외부 의존성 장애 — 로그 부재 자체가 단서인 경우
- **간헐 장애**: 에러가 낮은 비율로만 발생해 온셋 순서가 무의미한 경우

이 확장에서 LLM 에이전트 vs 휴리스틱의 격차가 정량화되면, 그것이 곧
"이 문제에 LLM을 쓰는 이유"의 증명이 된다.

## 실행 방법

```bash
# 오프라인 (베이스라인)
fivewhys evaluate --engine scripted --runs 3

# Claude 에이전트 (ANTHROPIC_API_KEY 필요)
fivewhys evaluate --engine claude --runs 1 --output docs/EVAL_CLAUDE.md
```
