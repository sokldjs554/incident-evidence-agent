# 장애 보고서: 캐시 재시작 후 스탬피드로 인한 DB 과부하 (2025-01-17)

## 요약
2025-01-17 11:02 ~ 11:48 동안 상품 조회 API의 지연과 오류가 급증했다.
Redis cache 노드를 워밍 없이 재시작하면서 캐시가 전부 소실되었고, 캐시 미스가
일제히 DB로 몰리는 cache stampede가 발생해 mysql 커넥션 한도가 고갈되었다.

## 영향
- 상품 조회 p99 지연 12초, 오류율 최대 38%
- mysql Too many connections로 무관한 서비스 2곳도 간헐적 실패

## 타임라인 (KST)
- 11:00 redis-cache 노드 재시작 (메모리 파편화 정리, 계획 작업)
- 11:02 캐시 미스율 3% → 96% 급등
- 11:05 mysql slow query·커넥션 수 급증
- 11:11 mysql Too many connections (max_connections 도달)
- 11:30 트래픽 일부 차단 후 캐시 수동 워밍 시작
- 11:48 미스율 정상 범위 복귀, 장애 종료

## 근본 원인
계획 재시작 절차에 캐시 워밍/점진 전환 단계가 없었다. 콜드 캐시 상태에서
전체 트래픽이 유입되며 동일 키에 대한 중복 DB 조회가 폭증(stampede)했고,
DB 커넥션이 고갈되며 캐시와 무관한 쿼리까지 실패했다.

## 5 Whys
1. 왜 상품 조회가 실패했나? — mysql이 Too many connections로 신규 연결을 거부했다.
2. 왜 커넥션이 고갈됐나? — 캐시 미스가 폭증해 모든 조회가 DB로 직행했다.
3. 왜 캐시 미스가 폭증했나? — redis-cache 재시작으로 데이터가 전부 소실되었다.
4. 왜 소실 상태로 트래픽을 받았나? — 재시작 절차에 워밍/점진 전환 단계가 없었다.
5. 왜 절차가 미비했나? — 캐시를 '있으면 좋은 것'으로 보고 장애 도메인으로 관리하지 않았다.

## 재발 방지 대책
- [완료] 캐시 재시작 런북에 사전 워밍 + 점진 트래픽 전환 절차 추가
- [완료] 캐시 TTL에 지터(jitter) 적용으로 동시 만료 방지
- [완료] DB max_connections 도달 전 서킷브레이커 동작 검증
- [진행] 핫키 목록 기반 자동 워밍 스크립트 구축
